# A1599：匹配 C0 后的 coherent 输出快照候选

**已闭合有界 CPU 只读快照的最小契约，并在同一新候选中完成实现、回归和模块构建。** 本候选具有在下次获批单帧试验中取得像素快照的机会，不需要先做一次“只验证分类”的设备试验。

需要纠正上一版的限制：未完全逆向 Apple `deviceUnlockSurface`，不等于 Linux 不能读取自己的 `dma_alloc_coherent()` 分配。标准 DMA API 允许此类分配的 CPU/device 并行访问。只读采样的内存访问契约与完整帧正确性、永久 DMA 静止是不同结论。

## 1. 当前 Linux 输出分配和 CPU 读取契约

已读当前实际源码，不依赖名称猜测：

| 代码位置 | 确认的事实 |
|---|---|

| harness `a1599_ring_read_reg32()` | 使用默认属性 `devm_ioremap_resource()` + **readl**，不是 readl_relaxed。 |

Linux 官方文档明确：coherent 分配允许 CPU 与设备并行访问并观察彼此已写入的数据，不要求 streaming cache-sync 操作；coherency 本身仍不替代内存顺序。这里不加入 `dma_sync_single_for_cpu/device`，也不 unmap/remap backing。[DMA API HOWTO](https://docs.kernel.org/core-api/dma-api-howto.html#types-of-dma-mappings)、[DMA API](https://docs.kernel.org/core-api/dma-api.html#part-ia-using-large-dma-coherent-buffers)

官方屏障文档将共享一致内存顺序与 MMIO 顺序区分开；默认映射上的 readl 对随后普通内存读取有顺序保证。新实现保留 readl 并在每次数据复制前使用 dma_rmb；不把单独一个屏障说成固件已经完成全部 DMA 的证明。[Linux memory barriers：DMA barriers 与 I/O accessors](https://docs.kernel.org/core-api/wrappers/memory-barriers.html)

以上依据包括当前用于编译的本地 Linux 文档、实现和配置，其 SHA 清单为 `build/LINUX-DMA-EVIDENCE.json`。该源码目录不是 Git checkout，未虚构 commit ID。当前分配路径与 API 已足以支持只读诊断采样；设备是否正确写到了该 backing、VXD 内部 MMU/DMA 路由是否完全正确，仍由设备试验及像素验证检验，未在本次宣称已证明。

timer 对照使用 Apple 官方 XNU 4903.241.1 源码，只作对应关系核验；不把这个公开 tag 宣称成整份 kernelcache 的完全相同源码。[IOTimerEventSource.cpp](https://raw.githubusercontent.com/apple-oss-distributions/xnu/xnu-4903.241.1/iokit/Kernel/IOTimerEventSource.cpp)

原始指令证据见 `build/APPLE-TIMER-COMPLETION-TRACE.txt`、`APPLE-C0-DOWNSTREAM-INSTRUCTIONS.txt`、`APPLE-C0-DOWNSTREAM-STRINGS.json`。

**C0 的可用含义：**它进入原厂当前任务/帧的完成通知链，区别于单纯 H2M consumer 已消费。我们的 fixture 是单个 progressive I picture、一个 slice、一个 ID81 group、唯一 outstanding fence=1。正常 C0 匹配 fence 为采样触发条件有充分宿主实现依据。但原厂也能聚合多条 C0，所以不能泛化成每条 C0 都证明所有场景的整个图像/所有后续 DMA 已完毕。

`LastMB=3` 与32x32的4个宏块在数值上相容；当前正常分流没有用这个值证明帧完整，未独立证明其编码语义。新代码只记录该字段，**不把它作为索引、长度、地址或完成谓词**。

在已追出的原厂正常路径里，没有发现另一次硬件完成消息等待或独立 VXD 完成轮询；timer 取消已排除。surface 虚调用内部尚未完整逆向，不能声称整个调用树绝无内部同步。但这不再是读取 Linux 自有 coherent 分配的硬前置条件：新方案不会 CPU 写回、释放、unmap 或把内存交给下一任务，只做有界观察。永久 DMA 静止仍明确未证明。

## 3. 当前最小快照实现

入口仍是已有 default-off `allow_output_export`，不能通过当前驻留模块热开新代码。保留单次 decode/资源 pin/M2H consumer 不推进策略。

1. 原有 ID81 submit 成功且 after-ID81 ring observation 成功。必须已发布、H2M已消费、收到合法C0、expected fence=1、原厂 class10、无 error detail、长度12、捕获 read/write=0/3。flags允许非零，bit27必须清零。
2. 核对 OUTPUT 恰为本设备原 `dma_alloc_coherent` 的 CPU返回指针和DMA handle，alloc/view/lifetime三份记录相符、大小4096；要求 hardware_started 和 lifetime.started。不会把 bus address 当 CPU指针。
3. 新 helper 观察固定六个环寄存器；要求既有 descriptor/start/capacity、H2M=10/10、M2H=0/3。dma_rmb 后把4096 bytes复制到宿主副本A；在A中检查 `[3072,4096)` guard。异常即停止。
4. 等待50ms，只再做一次采样。再观察环、dma_rmb、复制4096 bytes到副本B；检查B中guard并比较完整A/B。任何变化都不发布。
5. 最后再观察同样六个环寄存器；额外消息、consumer/descriptor变化或读错误均拒绝，不重试。用 smp_store_release 发布 immutable A；sysfs 用 smp_load_acquire 后读取，**导出过程中不再触碰 live backing**。

**额外工作上界：**两次4KiB CPU只读复制，共8192 bytes；一次50ms间隔；最多三次六寄存器观察，共18个readl。没有新增设备写、kick、ring payload重读、consumer推进、backing写入、释放或第二次提交。50ms只是两次样本的间隔，不是固件完成的超时证明；调度可能延长实际间隔。

所有失败均保持 snapshot_ready=false；若用户显式请求输出而采样失败，decode_once 返回该输出错误，同时日志分别保留原响应ret与 `output_snapshot_ret`，不会伪造 firmware error。成功只称 `snapshot_kind=bounded_read_only`；仍输出 `future_dma_quiescence=unproven pixels_compared=0 decode_success=unclaimed`。

三层事实不会混用：合法正常C0是触发条件，guard/两次样本一致是快照资格，实际图像是否正确由软件参考逐像素比较决定。即使设备后来又写 backing，已经发布的宿主副本仍保持不变；这不意味着后来DMA已停止。
