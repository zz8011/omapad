# A1599 codec firmware evidence — supplied static report

This file preserves the text of the parallel cloud task's report delivered to
this task on 2026-10-12. It contains no Apple firmware bytes, extracted kexts,
or raw debug strings. The assertions below are attributed to that report; the
raw extraction is not present in this workspace for an independent re-hash.

## Scope and result

The examined firmware is iOS 12.5.7 build 16H81, older than the user's
reported iOS 12.5.8. The parallel task performed static range retrieval and
analysis only. It did not load firmware, run the extracted binaries, write
hardware registers, or modify the user's computer or iPad.

Result: **go for a bounded static reverse-engineering feasibility pass; no-go
for a ready-to-port or working A7 Linux codec claim.** Exact-board Apple
artifacts establish both codec nodes and matching kext personalities. No
matching public firmware command ABI or Linux implementation was verified.

## Exact-board identity and artifact validation (reported)

Apple CDN restore URL:

https://updates.cdn-apple.com/2023FCSWinter/fullrestores/032-14259/9C1F915D-438F-4736-A120-F6F6B55EB586/iPad_64bit_TouchID_12.5.7_16H81_Restore.ipsw

The report says it retrieved by HTTP Range only the ZIP directory,
BuildManifest.plist, `DeviceTree.j85map.im4p`, and
`kernelcache.release.ipad4bm`. The complete 2,954,184,356-byte IPSW was not
downloaded. ZIP sizes and CRCs were checked. BuildManifest identifies
iPad4,7 / j85map / CPID `0x8960` / BDID `0x32`. The kernel IM4P payload was
reported as unencrypted `complzss`; decompression yielded 27,192,152 bytes,
matching Adler32 and ARM64 Mach-O validation. Decompressed kernel SHA-256:

`0e0b42b00f69d87bcd2d1b62baf769c040513c4cced275275350f9b58c1cf3a1`

The complete DeviceTree parse reportedly consumed exactly 100,736 bytes and
contained 125 nodes. The kernelcache was merged and stripped: module index,
personality and code-slice identification do not mean AppleVXD393 exists as an
independently extractable kext Mach-O.

The report states the `arm-io` ranges map child address 0 to parent

## Firmware / command hints

The VXD393 decoder's strings reportedly include `MSVDXDevInit`, `MSVDXStart`,
MMU references, and firmware-loading references. This supports searching
MSVDX-related material for conceptual correspondences. It does **not** prove
Intel Poulsbo firmware ABI compatibility, register-map identity, ring layout,
message IDs, or that a matching executable firmware blob is available for
Linux. A later cloud static review adds a register-level crosswalk, recorded
below. Those findings remain static; no hardware registers were accessed.

## Cloud static VXD393 ↔ Poulsbo register/ABI comparison

The parallel report compares AppleVXD393 code slices against public Poulsbo
MSVDX sources. These are reported findings, not live-device validation:

| Area | Reported finding |
|---|---|
| MTX register access | Register pair `0xf8` / `0xfc` overlaps. |
| MTX RAM upload | Register sequence `0x104` / `0x108` / `0x10c` overlaps, including bank-control fields. |
| MTX interrupts | MTX interrupt handling shows register-level/flow correspondence; full status/ack and error behavior still needs comparison. |
| Firmware comms signature | Address differs: VXD393 `0x2fe0`, Poulsbo `0x2cc0`. |
| Ring indices | Definitions differ; do not assume a shared PSB ring struct. |
| Buffer addressing | VXD393 obtains buffers through descriptors. |
| Message length | VXD393 uses a 7-bit length field; PSB uses 8 bits. |

This supports shared MTX/register lineage and possible reuse of narrowly
isolated register-helper concepts, not a drop-in driver or firmware match.
Complete H.264 command payloads, firmware format and redistribution rights,
DMA/MMU mapping, Linux clock/reset integration, and equivalence to iOS 12.5.8
remain unresolved. Protected-content paths are out of scope; ordinary
unprotected H.264 decode is the target.

The next static crosswalk should establish, with byte/structure evidence:

1. VXD register offsets and bitfields versus licensed PVDEC/MSVDX headers.
2. Firmware container, code/data placement, MTX boot handshake and version.
3. Command ring dimensions, producer/consumer indices, message framing,
   fences, cache barriers and failure/reset behavior.
4. MMU/DART stream/context, page tables, address width, invalidation, DMA
   ownership and cache-coherency rules.
5. Clock/power/reset ordering, plus exact interrupt-parent encoding and IRQ
   status/ack semantics.

No register access is part of that static phase. Equivalence of the iOS
12.5.7 results to the user's iOS 12.5.8 installation is also unverified.

## Public implementation leads and limits (reported)

### Intel/Imagination Poulsbo MSVDX

The report identifies `gregkh/psb-kmp` files `psb_msvdx.c`, `psb_msvdx.h`,
and `psb_msvdxinit.c` as carrying permissive MIT-style notices with Intel and
Imagination copyrights. They contain MTX firmware upload, message handling,
register macros and reset/clock sequences. They explicitly support Poulsbo
D0/D1, use `msvdx_fw.bin`, and are integrated with old DRM/TTM/PCI. These can
serve as a register/firmware comparison source, not a verified A7 match.
`psb_drv.c` is GPL-2.0, so the repository is mixed-license. Current mainline
gma500 KMS sources do not contain the MSVDX codec implementation.

- https://github.com/gregkh/psb-kmp/blob/master/psb_msvdx.c
- https://github.com/gregkh/psb-kmp/blob/master/psb_msvdx.h
- https://github.com/gregkh/psb-kmp/blob/master/psb_msvdxinit.c
- https://github.com/gregkh/psb-kmp/blob/master/psb_drv.c
- https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/gma500/Makefile

### Intel AOSP PSB VA-API userspace

The report points to Intel's AOSP `psb_video` as userspace VA-API code. Its
`configure.ac` is reported as permissively licensed and depends on libva,
libdrm, libwsbm and X11; the firmware tree includes MSVDX and Topaz variants.
An Android.mk source mirror reportedly defines PSBVIDEO_VXD392 and
Merrifield/Moorefield/Morganfield paths. VXD392 is adjacent family evidence,
not proof of VXD393 compatibility. This is a userspace/platform integration
lead, not an A7 Linux kernel driver.

- https://android.googlesource.com/platform/hardware/intel/img/psb_video/
- https://android.googlesource.com/platform/hardware/intel/img/psb_video/%2B/refs/tags/android-o-mr1-iot-release-smart-clock-fcs/configure.ac
- https://github.com/codeaurora-unofficial/platform-hardware-intel-img-psb_video/blob/LA.AF.1.1.c1/src/Android.mk (mirror cited by source report)

### TI/Imagination V4L2 VXE/VXD

The report identifies TI's `ti-linux-6.6.y` `drivers/media/platform/imagination/vxe-vxd`
as GPL-2.0 V4L2 code targeting D5520MP2 decoder and VXE384MP2 encoder. It
contains PVDEC/MSVDX headers, firmware interfaces, Topaz encoder headers and
an encoder firmware C array; the decoder loads `pvdec_full_bin.fw`. It depends
on V4L2 mem2mem/videobuf2, runtime PM, DMA, IMG memory-manager/MMU, firmware
and platform resources. These are not the VXD393/VXE380 identities observed
in the A7 kexts, so the framework and design patterns may guide a Linux API
implementation, while register maps, firmware and ABI require proof.

- https://github.com/TexasInstruments/ti-linux-kernel/tree/ti-linux-6.6.y/drivers/media/platform/imagination/vxe-vxd
- https://github.com/TexasInstruments/ti-linux-kernel/blob/ti-linux-6.6.y/drivers/media/platform/imagination/vxe-vxd/decoder/vxd_pvdec_regs.h
- https://github.com/TexasInstruments/ti-linux-kernel/blob/ti-linux-6.6.y/drivers/media/platform/imagination/vxe-vxd/decoder/img_vdec_fw_msg.h
- https://github.com/TexasInstruments/ti-linux-kernel/blob/ti-linux-6.6.y/drivers/media/platform/imagination/vxe-vxd/decoder/vxd_core.c
- https://github.com/TexasInstruments/ti-linux-kernel/blob/ti-linux-6.6.y/drivers/media/platform/imagination/vxe-vxd/encoder/fw_headers/topazscfwif.h
- https://www.ti.com/lit/ds/symlink/tda4vm.pdf (sections 7.3.4/7.3.5)

## Bounded conclusion

Ordinary unprotected H.264 decode is the relevant goal; FairPlay/LSKD and
protected-content paths are out of scope. The evidence justifies a bounded
static feasibility pass. It does not justify claiming a ready A7 Linux driver,
reusing another core's firmware, or touching MMIO. Preserve the existing H.264
30 FPS implementation. The user later reported the iPad battery was depleted
and the USB link disconnected; a read-only host check found no runner/recorder,
and target-side status was not checked. Continue static analysis and compare a
separately verified 12.5.8 component set when available.
