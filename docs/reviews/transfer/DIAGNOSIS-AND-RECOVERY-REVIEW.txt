2. FILE-ERR request 的确切含义与不确定性
固定镜像接收器启动即发 READY，收到 HELLO 再发 READY。
非法请求语法/文件名/长度产生 FILE-ERR request。合法 PUT 进入 receive_file，先发 FILE-READY，之后等待载荷。
原发送器把首次读取到的 READY 作为 HELLO 响应，随后立即发 PUT。它允许额外一次 READY，但不允许 ERR request；遇到后立即停止，因此可能仍有未读响应。
已捕获 ERR request 确实是协议错误行，不能简单说只是多余 READY。
然而协议没有 request ID，该错误行无法从当前前缀归属到本次 HELLO 或 PUT。首个 READY 也可能是启动时留下的。
仅凭当前前缀，不能回答“PUT 已获准”或“目标拒绝本次 PUT”；两种判断都会越过证据。
不能断言当前仍等待 payload。若已获准，原实现有 30000ms 无数据超时，但实时进程/队列状态未采样。

从固定 gadget-fix initramfs cpio 解出 sbin/file-recv，SHA256=7515a14756613d825258a4022318fc2c127a1b53357470010b146181d5e08d05。
原 AArch64 ELF 经现有 qemu-aarch64-static + 同版本 musl 在软件 PTY 中执行，仅写临时目录；没有 USB、内核模块加载或固件执行。
正常输入完全相同的 48-byte TX：READY(startup), READY(HELLO), FILE-READY。由此排除该确定字节串本身被固定 parser 拒绝。
显式注入一份启动 READY 的 CRLF 回显后，再发相同 TX：READY, ERR request, READY, FILE-READY。前 35 bytes 与实机完全一致。
注入是一个可行机制的反例，不是实机 host ECHO=1 的证据；现场打开前 termios 未记录，也没有设备收到的请求副本。
等待原二进制完整 30 秒超时，取得 FILE-ERR transfer，临时目录为空；同一进程 HELLO→READY，新的单次 PUT→FILE-READY，收到原 1211 模块 872744 bytes 后 CRC ACK 正确，目标临时文件 SHA 与原模块一致。测试随后结束并清理软件临时目录；没有加载模块。
REPRODUCTION.json 保留每条响应及相对时间。reproduce.py 可复现以上两个情形。
这说明同 RAM/同进程恢复在协议实现上可行，不意味着现场前置条件已经满足。

6. 独立终审修订（优先于第4节的简略建议）
审核全文见 INDEPENDENT-REVIEW.txt。诊断结论获支持；尚无可直接执行的恢复实现。
- “receive-only”只表示不调用应用 write，不能保证线路零 TX：打开到设 raw 的窗口和关闭时恢复 ECHO 都可能自动回显。不得直接复用原 RecordedLink 并宣称纯被动；必须明确 termios/close 策略及风险。
- 2 秒/4096B 只是读阶段建议。实现需整体监督期限，涵盖初始化、身份检查、fsync、restore/close；超时不能触发重开或重试。原 read 一次8192B，若越过总上限应完整落盘该块后失败，不截断证据。
- 目标接收器由 init respawn；记录 PID/starttime/exe/FD/wait 状态。没有前次 PID/starttime 时，只能确认同 RAM，不能确认同进程。
- 空 incoming 目录、唯一进程或一般 poll/read 等待均不足确认 parser 命令态；必须结合队列尾部和接收器状态闭合。未闭合时不能发 HELLO，更不能 PUT。
